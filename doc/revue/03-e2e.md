## 1. Résumé

**Note : 4/10. Verdict : NE PAS remplacer le Shinken master de production en l'état.**

Le cœur du moteur tourne bien en Python 3. Les 6 daemons démarrent sans traceback, se connectent entre eux et prennent leur configuration. Les checks s'exécutent, les états passent de SOFT à HARD et les perfdata remontent. Les event handlers, les notifications (avec une commande locale), les ACK, les downtimes et les checks passifs via Livestatus fonctionnent aussi. L'arrêt par SIGTERM est propre.

Avec la configuration **livrée** dans le dépôt, en revanche, plusieurs fonctions indispensables en production sont cassées ou absentes :

1. **Livestatus ne démarre jamais (bloquant).** Le dernier commit fait pointer `livestatus` vers `logstore-sqlite`, un module qui n'existe pas dans `modules/`. Le module plante (`IndexError`) et redémarre toutes les 5 s, sans fin. Le port 50000 ne s'ouvre jamais. Conséquences : pas de Thruk, et plus aucun moyen documenté d'envoyer une commande externe (ACK, downtime, force check).
2. **Aucune rétention (bloquant).** Aucun module de rétention n'est livré ni configurable. Un redémarrage du scheduler, ou un reload (redémarrage de l'arbiter), **perd tous les états, ACK, downtimes et résultats passifs**. Toutes les notifications de problème sont alors **renvoyées**, y compris pour les éléments acquittés ou en downtime.
3. **Notifications e-mail cassées (bloquant).** `notify_by_email.py` est appelé via `$PLUGINSDIR$=/var/lib/shinken/libexec`. `libexec/` n'est ni dans le wheel ni copié par le Containerfile : `Fail launching command`, aucun mail ne part.
4. **Majeur.** Après un `kill -9` du poller, ses workers orphelins gardent le port 7771. Le nouveau poller ne peut plus se lier au port et meurt (`PortNotFree`) : les checks restent arrêtés tant que les orphelins ne sont pas tués à la main.

Ce qui manque pour un remplacement sûr : un logstore valide (revenir à `logstore-null` ou porter `logstore_sqlite`), un module de rétention porté en Python 3, et `libexec` installé (avec un MTA joignable).

## 3. Problèmes détectés

### Bloquants

**B1 — Livestatus en boucle de crash : le module `logstore-sqlite` n'existe pas**
- `etc/modules/livestatus.cfg:6` : `modules logstore-sqlite` (introduit par 6c25f5a) ; `etc/modules/logstore-sqlite.cfg` : `module_type logstore_sqlite`. Aucun répertoire `modules/logstore_sqlite/`.
- Plantage dans `modules/livestatus/module.py:169` (`add_compatibility_sqlite_module` suppose que le chargement a réussi) :
  ```
  WARNING: [broker-master] The module type logstore-sqlite for logstore-sqlite was not found in modules!
  File ".../modules/livestatus/module.py", line 169, in add_compatibility_sqlite_module
      self.modules_manager.instances[0].load(self)
  IndexError: list index out of range
  ERROR: [broker-master] The external module livestatus goes down unexpectedly!
  ```
- Impact : pas de Livestatus, donc pas de Thruk (doc/livestatus-thruk.md), pas de force check/ACK/downtime (doc/exploitation.md). La validation de doc/installation.md (« requête Livestatus brute ») échoue. `integration/podman-lab.sh` ne le voit pas, car il ne teste que la WebUI et remplace la liste de modules du broker.
- Correctif : revenir à `modules logstore-null` (testé : fonctionne), ou porter réellement `logstore_sqlite` en Python 3 et l'ajouter à `modules/`. Dans `module.py:161-169`, ne pas indexer `instances[0]` quand `load_and_init()` n'a rien chargé : journaliser une erreur et repartir sur logstore-null. Ajouter à `podman-lab.sh` un test Livestatus (`GET hosts`).

**B2 — Aucune rétention : état, ACK et downtimes perdus à chaque redémarrage du scheduler ou reload de l'arbiter**
- `etc/schedulers/scheduler-master.cfg` : `modules` vide ; `modules/` ne contient aucun module de retention (`pickle-retention-file-scheduler` etc.) ; `shinken/scheduler.py:1000-1012` ne fait qu'appeler `hook_point('save_retention'/'load_retention')`.
- Preuve (lab, redémarrage du scheduler à 1793446602) : ACK, 2 downtimes et résultat passif tous perdus, puis :
  ```
  [1793446642] HOST NOTIFICATION: labadmin;deadhost;DOWN;...      <- hôte qui était en downtime
  [1793446642] SERVICE NOTIFICATION: labadmin;labhost;StaticWarning;WARNING;...  <- service qui était en downtime
  [1793446651] SERVICE NOTIFICATION: labadmin;labhost;Flip;CRITICAL;...           <- service qui était acquitté
  ```
  Même chose avec la conf livrée (google.fr, cloudflare-dns renotifiés aux 3 contacts) et à chaque reload de l'arbiter (`CURRENT SERVICE STATE: ...;PENDING` à 1793446449). Une notification DOWN envoyée pendant le reload n'a ensuite jamais eu de RECOVERY.
- Impact production : chaque modification de conf, redémarrage de conteneur ou `podman restart` produit une rafale de notifications et efface les acquittements et les maintenances.
- Correctif : porter en Python 3 un module `pickle_retention_file` (scheduler) et le déclarer dans `scheduler-master.cfg` (`modules retention-file`, avec un fichier sur le volume `/var/lib/shinken`). Ajouter un test e2e « ACK + downtime survivent à un restart du scheduler ».

**B3 — Notifications e-mail : `notify_by_email.py` introuvable**
- `etc/resource.d/paths.cfg:6` : `$PLUGINSDIR$=/var/lib/shinken/libexec` ; `etc/commands/notify-*-by-email.cfg` et `detailled-*` l'appellent. `libexec/` n'est pas dans le wheel (`unzip -l` : absent), le `Containerfile` ne le copie pas, et `/var/lib/shinken` est un volume vide.
- Preuve (reactionner, conf livrée) :
  ```
  ERROR: [Shinken] Fail launching command: /var/lib/shinken/libexec/notify_by_email.py -n host -S localhost -r <e-mail du mainteneur> -f html -c 'PROBLEM,,github.com,...
  ```
  Le scheduler journalise pourtant `HOST NOTIFICATION: noel;google.fr;DOWN;notify-host-by-email;...` : rien de visible côté statut.
- Note : même avec le script présent, `-S localhost` suppose un MTA dans le conteneur, qui n'en a pas.
- Correctif : `COPY libexec/ /usr/local/lib/shinken/libexec/` dans le Containerfile, `$PLUGINSDIR$` pointant dessus, `chmod +x` ; rendre l'hôte SMTP paramétrable (variable de ressource `$SMTPHOST$`) ; test e2e de notification.

### Majeurs

**M1 — `kill -9` (ou OOM) du poller : les workers orphelins gardent le port, et le redémarrage échoue**
- 5 workers rattachés à PPID 1 après le kill ; l'un d'eux (`Sl`, 2 threads) intercepte SIGTERM sans sortir (`SigCgt` contient SIGTERM) et garde la socket d'écoute héritée.
- Nouveau poller : `shinken.http_daemon.PortNotFree: Error: Sorry, the port 17771 is not free ... [Errno 98] Address already in use` (shinken/http_daemon.py:117), puis le process sort. Aucun check exécuté tant qu'on n'a pas fait `kill -9` à la main sur les orphelins.
- En conteneur, `podman restart` tue tout le namespace, ce qui limite le risque. En natif ou en systemd sans `KillMode=control-group`, c'est un arrêt de supervision silencieux.
- Correctif : fermer la socket d'écoute dans les workers après le fork (ou `SO_REUSEPORT`, ou `set_inheritable(False)`), faire surveiller `os.getppid()` par les workers pour qu'ils sortent si le parent meurt, `prctl(PR_SET_PDEATHSIG)`.

**M2 — Lancement depuis les sources impossible**
- `bin/shinken-*:35-39` : `from shinken.cli_compat import optparse` est placé **avant** le bloc qui ajoute le checkout au `sys.path`, d'où `ModuleNotFoundError: No module named 'shinken'`. `bin/launch_*.sh` sont donc inutilisables sans `pip install`.
- `bin/shinken-arbiter:72` : `os.path.join(os.environ.get('PYTHONPATH',''), root)` construit un chemin au lieu d'une liste (il faut `os.pathsep`).
- Correctif : déplacer l'import après le bootstrap ; utiliser `os.pathsep.join(...)`.

**M3 — Le reload ne s'applique pas aux modules du broker (doc trompeuse)**
- `shinken/daemons/brokerdaemon.py:623` : `if not self.have_modules:`. Les modules ne sont chargés qu'une fois. doc/exploitation.md (« Relancer l'arbiter : il relit etc/ et redistribue tout seul ») est faux pour toute modification de `etc/modules/*` ou de la ligne `modules` du broker. Démontré : après correction de livestatus.cfg et redémarrage de l'arbiter, le broker continue de charger `logstore-sqlite`. Il a fallu redémarrer le broker.
- Correctif : le documenter (« modifs de modules → redémarrer broker »), ou recharger les modules quand la liste reçue change.

### Mineurs

- **m1 — Logs console pollués par des `b'...'` et doublés.** `shinken/misc/termcolor.py:139-140` encode en bytes avant `print`, d'où des lignes `[95mb'[1793445942] INFO: [Shinken] ...'[0m`. Chaque ligne est aussi émise une seconde fois par le handler racine de `shinken/structured_logging.py:92-101`. `podman logs` devient illisible et deux fois plus gros (broker.stdout : 237 ko en 3 min). Correctif : supprimer l'encodage et ne pas propager vers la racine (`propagate=False`), ou ne garder qu'un seul handler.
- **m2 — Traceback ERROR à chaque commande Livestatus.** `modules/livestatus/livestatus_client_thread.py:240` appelle `handle_wait_query(*response)` sur une réponse vide (`COMMAND`) : `TypeError: LiveStatusClientThread.handle_wait_query() missing 2 required positional arguments`. La commande est quand même exécutée. Correctif : `if not response: return` avant le test, et ne traiter comme wait-query qu'un `tuple`.
- **m3 — `SyntaxWarning: invalid escape sequence`** dans `shinken/objects/config.py:935-1037`, `external_command.py:571-576`, `macroresolver.py:281-315`, `timeperiod.py:475-715`, `util.py:582-624`, `dependencynode.py:304`. Ces séquences deviendront des `SyntaxError` dans une future version de Python. Correctif : chaînes `r'...'`.
- **m4 — Processus enfants non attendus à l'arrêt.** Après SIGTERM, `[shinken-broker] <defunct>` et `[shinken-receive] <defunct>` sont rattachés à PID 1. tini les récupère en conteneur, ce qui n'est pas garanti en natif. Correctif : `join()` des processus de module dans `do_stop`.
- **m5 — Message parasite au démarrage** : `Stale pidfile exists at invalid literal for int() with base 10: ''`, sur un pidfile neuf.
- **m6 — À confirmer** : un `PROCESS_SERVICE_CHECK_RESULT` WARNING sur un service à `max_check_attempts 1` reste en état **SOFT** (`state_type=0`, `att=1/1`). Il faut comparer avec le master.
- **m7 — Perfdata entre guillemets en sortie CSV Livestatus** (`"value=42;5;10;0;100"`). La sortie JSON, utilisée par Thruk, est correcte.
- **m8 — Logs du poller et du reactionner vides au 1er run**, même en `log_level=INFO`. Au 2e run, `pollerd.log` contenait bien les WARNING. Diagnostic plus difficile.
- **m9 — Conf livrée avec des données personnelles et des cibles réelles** (contact `noel` → `<e-mail du mainteneur>`, hôte `KIKI` 158.69.204.23, `this-vps` → `host.containers.internal`) : un premier démarrage « tel quel » notifie de vraies adresses.
- **m10 — Sécurité / isolation.** Les daemons acceptent la configuration de n'importe quel arbiter qui atteint leurs ports (sans authentification, comme en amont). Pendant le test, un autre processus de la machine a poussé sa conf sur mes satellites des ports 7768-7773 : hôtes `KIKI`, `google.fr` apparus, et redispatchs `Scheduler scheduler-master did not managed its configuration 0`. En production, ne jamais exposer 7768-7773 hors du réseau des conteneurs (c'est le cas dans `compose.yaml`).

## 4. Ce qui fonctionne (rassurant)

Le moteur en Python 3 est sain sur le chemin nominal. Les points suivants ont été vérifiés :
- parsing et validation de la conf, dispatch arbiter vers les satellites (HTTP Cheroot + pycurl) ;
- ordonnancement et `interval_length` ;
- exécution des plugins et retours poller → scheduler ;
- états SOFT/HARD et dépendances hôte/service ;
- notifications et event handlers via le reactionner ;
- broks vers le broker (WebUI JSON) ;
- commandes externes Livestatus → broker → arbiter → scheduler ;
- downtimes et ACK pendant l'exécution ;
- détection d'un satellite mort et redispatch ;
- arrêt propre par SIGTERM.
